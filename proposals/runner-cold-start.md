# Fix the six seconds after Ready

*Proposal for FOL-29, 2026-10-17. Status: research and plan, nothing built. For Kousha (owns FOL-29) and the owner. Code references are to the repo heads read on 17 Oct: foldrun-core `ab2e940`, foldrun-platform `5e85c70`, foldrun-infra `c6ce963`. Every number carries a label: **(foldrun, measured)** comes from our own run records or code comments, **(independent)** is a third-party measurement, **(vendor)** is a provider's own claim, and **(inferred)** is this report's reasoning from those.*

> **Decisions, 17 Oct 2026 (owner).** AWS production is skipped for now; the box and staging carry the load. Order of work: per-phase timestamps first, then the start-up fixes below (FOL-29), then a warm pool of **slim small** pods only (86% of steps) built inside `run-k8s.ts` — single use, no tenant data until claim. The queue stays the Postgres `SKIP LOCKED` queue; its fairness rules and pod budget are fixed separately.

foldrun's pod cold start is already fast; the step is slow after the pod is up. Across 223 step attempts on dev.foldrun.io (11–17 Oct 2026), the pod went from `kubectl apply` to Ready in **p50 0.86 s / p95 3.4 s**, but from Ready to the driver's first output took **p50 6.1 s / p95 17.9 s**, and from "step started" to the first model output took **p50 7.7 s / p95 33 s** (foldrun, measured). The 0.86 s already sits in the 0.5–1.0 s band that the best hosted sandboxes reach in an independent burst benchmark ([ComputeSDK, 16 Oct 2026](https://computesdk.com/benchmarks/sandboxes/burst-tti)), so the seconds that matter are a hard-coded 2 s NetworkPolicy wait, six sequential `kubectl cp` calls and two `exec`s, the root shim's `chown -R`, about 13 core imports, the Claude Agent SDK's own start-up calls and the first model turn — none of which is timed separately today. The tails come from two other places: parallel bursts (with 3–6 other pods applied within 3 s, Ready p95 rises to **12.9 s**) and cold account search/browser pods, which are ensured *before* the run pod is applied and add **p50 10.7 s** to the steps that wait for one. That means the industry's headline fix, a warm pod pool, would save only **~0.9 s at p50 on the box** unless the pool also has the files, the policy and the driver staged before the step claims it. The recommendation is therefore ordered: instrument every phase first, then overlap account-pod start with the run pod, collapse the copy-in, replace the fixed 2 s wait with a verified gate, trim the driver and SDK start, stop releases from invalidating apt snapshots, and pre-pull images — all within the owner's constraints and none needing a decision — and only then decide on a warm pool, which the owner skipped for AWS on 24 Sep and which this report raises as a question, not an assumption.

## Pod start is 0.86 s; the step waits 7.7 s for its first model output

The step lifecycle is one fresh gVisor pod per attempt, driven by the worker through about ten sequential `kubectl` subprocesses. The worker creates the namespace (on every step), stages the workspace into a host temp directory, ensures the account's search or browser pod if the step uses `web`, then applies the pod, waits for Ready, runs six `kubectl cp` calls (workspace, library, input.json, in.json, env.sh, mtimes.json), runs an `exec` to put file times back, waits until at least 2000 ms after Ready, and finally `exec`s `touch go` (`foldrun-platform/src/run-k8s.ts:736-875`). The 2 s wait exists because "a request in the first ~0.3 s reaches an address every policy forbids", measured on k3s with kube-router on 6 Sep 2026 (`run-k8s.ts:866-873`). Inside the pod, a root shim polls for `go`, installs the egress CA, starts a `node -e` to read `runtime.system`, restores or builds apt packages, starts the install helper, runs `chown -R agent:agent` over the copied trees and drops to `agent` (`run-k8s.ts:159-171`). The driver then performs about 13 dynamic imports of core, prepares the language runtime, builds the MCP tool servers in-process, and calls `query()` from `@anthropic-ai/claude-agent-sdk` (`foldrun-core/src/run-container.ts:498-702`). The number the code calls "the cold-start number" is only apply → Ready (`run-k8s.ts:850-852`).

The live data shows where the time goes. These are 223 attempts from 66 run records in 19 workspaces of one account on the dev install, pulled read-only from `GET /api/workspaces/<ws>/runs/<id>`; all figures are (foldrun, measured).

|---|---|---|---|---|
| step started → pod apply (host prep, account pods) | 0.45 / 7.59 / 19.8 | 0.40 / 3.57 | 1.42 / 19.3 | 0.58 / 4.18 |
| apply → Ready (`sandboxMs`) | **0.86** / 3.38 / 25.4 | 0.86 / 3.73 | 0.84 / 1.29 | 1.00 / 1.48 |

Three readings follow. First, **the image does not matter on the box**: full (1.7 GB) reaches Ready in p50 1.00 s against slim's 0.86 s, because both images already sit in containerd on the one node, and Ready → first output is about 6 s on every variant. Second, **the post-Ready phase is about seven times the measured cold start**, and its floor is the coded wait: the smallest `firstOutputMs` in the sample is 2.64 s. Third, **start-up is a material share of desk runs**: summed prep + sandbox + first output across a run's steps is p50 27% of the run's wall time (an upper bound, because parallel groups overlap).

Nothing in the records splits the 6.1 s further, because there is no timestamp for "go written", "driver started", "SDK `query()` called" or "first model token", and `firstOutputAt` counts the first parseable protocol line of any kind, so an informational `runtime:` line counts as "first output" (`run-k8s.ts:923`). One subset gives a rough split. On the 25 attempts that used a shared runtime, the runtime info line is the driver's first line and arrives at p50 2.97 s after Ready, while the first tool or text event arrives at p50 6.94 s (foldrun, measured). Read together with the coded floor, that suggests the following budget, which is **(inferred)**: medians do not add exactly, the copy-in runs *inside* the 2 s floor rather than after it, and the shared-runtime subset overlaps one burst.

| Segment | Rough p50 | Basis |
|---|---|---|
| step started → apply | 0.45 s | measured |
| apply → Ready | 0.86 s | measured |
| Ready → `go` (six `kubectl cp` + mtimes `exec`, inside a ≥2 s floor) | ~2.0 s | coded floor; minimum observed 2.64 s |
| `go` → runtime ready (shim, `chown -R`, node start, ~13 imports, `prepareRuntime`) | ~1 s | shared-runtime line at 2.97 s after Ready |
| runtime ready → first model output (MCP builds, SDK/CLI spawn and bootstrap calls, the model's first turn) | ~4 s | 6.94 s − 2.97 s on the shared-runtime subset |

The biggest single block is therefore probably the SDK start plus the first model turn, and part of that is the model itself, which no infrastructure change removes. The trails do show the SDK's own start-up traffic through the egress proxy: `GET api.anthropic.com/api/claude_cli/bootstrap` at p50 341 ms and `HEAD /api/hello` at p50 261 ms, plus event-logging and Datadog intake connections (foldrun, measured, counted in the 66 records); whether they block the first `messages` request is not known. The first job of FOL-29 is to make this split measured rather than inferred.

The tails have two causes that are plainly visible in the data. **Bursts**: with no other apply within ±3 s (n=128), Ready is p50 0.88 / p95 1.39 s and first output p95 9.9 s; with 3–6 others (n=35), Ready is p50 1.79 / **p95 12.9 s** and first output p95 18.5 s. The worst cases were two parallel `validator` steps on one desk at 25.4 s and 25.1 s to Ready (16 Oct, 19:06 UTC, four applies within 3 s) and a `post-writer` fan-out of six pods on another desk on 12 Oct (Ready 4.6–7.7 s, first output ~18 s) (foldrun, measured). Every step in a burst spawns its own string of `kubectl` processes against one API server on one 8-CPU node, each run pod requests only `cpu: 100m` with no CPU limit (`run-k8s.ts:417-437`), and gVisor boots and NFS mounts all land at once (inferred). This matches an independent report that gVisor pod start grows near-linearly with concurrency: 6.7 s at 25 pods and 17.0 s at 100 on EKS with Istio, 3.4 s at 50 without ([google/gvisor#13395, 9 Jun 2026](https://github.com/google/gvisor/issues/13395)). **Cold account pods**: a step that grants `web` waits synchronously for the account's search or browser pod before its own pod is applied (`run-k8s.ts:671-716, 803-813`). The 15 attempts that started one spent **p50 10.7 s / p95 19.6 s** in host prep, against 0.43 / 3.34 s for the other 208; browser first start alone was p50 4.55 s (max 18.3 s) and search p50 6.55 s (foldrun, measured).

Two more costs sit off the sample but on the path. The runner image tag is a hash of the driver, Dockerfile and every file of core's built `dist/`, so **every core change produces a new runner tag** (`run-container.ts:990-1000`), and the apt snapshot key includes a checksum of the image's dpkg status (`foldrun-core/src/runtime.ts:650-713`). The research inferred that a release therefore invalidates every apt snapshot, so the first `runtime: system:` step per package set after a release pays apt again: **23–30 s through apt against 0.76 s from the snapshot** for a 154-package, 432 MB set (code comment, 11 Oct 2026, gVisor on NFS), or 37 s against ~1 s for ffmpeg and manim (FOL-29). That inference holds only if a rebuild changes dpkg status, which depends on whether the apt layer is rebuilt or served from build cache; comparing the dpkg status checksum across the 5 full and 8 slim runner tags still on the box settles it in minutes. No attempt in the sample used `runtime: system:`, so FOL-29's "runtime: system: agent" cell has no live data yet. Separately, the deploy-time runtime warm pod that pre-builds environments was evicted on 17 Oct for exceeding its 2 Gi ephemeral-storage limit (box events, read-only), because warm pods run at size `small` (`foldrun-platform/src/runtime-warm.ts:127`); when that warm fails, the first real step builds instead.

## Every fast platform pre-warms something generic and binds the tenant late

Start time on any platform splits into placement (scheduling or node provisioning), image fetch, sandbox boot and application init. The systems FOL-29 names attack those phases in four ways: keep capacity warm that has never served anyone, keep images close to or lazily loaded on the node, snapshot an initialised sandbox and restore it, or reuse an environment across requests. The pattern under all of them is the same. **No provider pre-warms with tenant data in place.** The warm or snapshotted unit is generic per image or per version, and the tenant's inputs, secrets and network identity arrive after the claim or restore. AgentCore snapshots at the first healthy `/ping`, before any session exists; the agent-sandbox template forbids env injection by default, and a claim that sets `env` or `volumeClaimTemplates` is "always cold-started" ([sandboxclaim_types.go](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/extensions/api/v1beta1/sandboxclaim_types.go)); Anthropic's own managed-agents reference on agent-sandbox POSTs `{session_id, work_id}` to a listener in the pre-warmed pod and lets the worker fetch its workspace after binding ([agent-sandbox use case](https://agent-sandbox.sigs.k8s.io/docs/use-cases/anthropic-managed-agents/)). ARC does the same with a single-use JIT registration token per ephemeral runner. That is good news for foldrun, because it already resolves bound secrets at the egress proxy so the pod never holds them; a claimed pod only needs the proxy to learn "this pod is now run R, step S".

Three findings matter more than the leaderboard. First, **vendor headline numbers are restore-only and 5–15× below measured end-to-end start**: E2B's "~80 ms" became 0.44–1.25 s and Daytona's "<90 ms" became 0.72 s when ComputeSDK timed `create()` to the first successful command, and E2B fell from first in March to twentieth in October ([ComputeSDK](https://computesdk.com/benchmarks/sandboxes/burst-tti)). The yardstick for foldrun is the independently measured 0.5–1.0 s band, which our 0.86 s Ready already meets when there is no burst. Second, **gVisor is not the cold-start problem**: Google documents its gVisor-based gen1 Cloud Run as having faster cold starts than its microVM gen2 ([Cloud Run docs](https://docs.cloud.google.com/run/docs/about-execution-environments)), and a gVisor maintainer calls ~300 ms for a full `runsc run` "a reasonable approximation" of the current state ([google/gvisor#13182](https://github.com/google/gvisor/issues/13182)). Third, **the techniques that cut seconds elsewhere attack image pull and placement, which the box does not pay**. SOCI's 4–9× gains and Lambda's chunk caches exist because Fargate and Lambda fetch images per start; on a long-lived node with two shared images, a pre-pull removes the pull completely, and SOCI's own authors note that images under ~250 MB compressed may start *slower* with lazy loading ([AWS Containers blog, 2023](https://aws.amazon.com/blogs/containers/under-the-hood-lazy-loading-container-images-with-seekable-oci-and-aws-fargate/)).

The vendors' prices also show what warmth costs when someone else runs it: a provisioned Lambda GB-second idles at about 43% of its busy rate, and an idle Cloud Run min instance at about 10% of the active CPU rate (figures above). On the box the comparable cost is small: an idle run pod requests 100m CPU, and its real idle memory with a pre-imported driver is unmeasured. On AWS the real cost is not the pods but keeping a runner node up.

## A warm pool buys 0.9 s on the box unless it also stages files, policy and driver

A warm pool of pre-started, never-used pods fits "sandbox destroyed after each step, never reused across steps": the pod is claimed once, bound to one step, and destroyed after, exactly like an ARC ephemeral runner. But a pool of plain Ready pods removes only `sandboxMs`, which is **0.86 s at p50** on the box (foldrun, measured), because everything after Ready still happens after the claim: the copy-in, the 2 s policy wait (which keys off Ready today), the shim, the imports and the SDK start. The pool earns its keep only if it is built to move three more things off the claim path. Files: a running pod cannot gain volumes or env, so the workspace must arrive over a single late-bind channel (one tar stream) rather than six `kubectl cp` calls. Policy: a pool pod that has been up for minutes already has its NetworkPolicy in force, so the 2 s wait disappears, but only if the claim does not change the policy that pod is under; foldrun's per-step `network:` allowlist lives at the egress proxy, so the pod-level policy can plausibly stay generic (inferred; check against the current policy manifests). Driver: the pool pod can be parked with node started and core imported, waiting on the bind, which removes roughly the ~1 s "go → runtime ready" segment (inferred). With all three, the pool could take roughly **3–4 s off the p50** and most of the burst tail, where Ready p95 reaches 12.9 s, provided the pool is at least as deep as the typical fan-out (six pods in the case above).

The safe shape is the one every provider uses. The pool pod carries no secrets, no workspace mount and no tenant labels, and holds egress closed or proxy-only until claimed. The claim delivers a single-use bootstrap token (ARC's JIT pattern), the listener accepts exactly one bind and closes, the egress proxy lease is attached to the pod's IP at claim time, and the platform deletes the pod at step end with a wait for full termination; a pod is never returned to the pool. agent-sandbox v1.0.7 (15 Oct 2026, API `v1beta1`, about 4.3k stars) already implements pool → claim → delete with ownership transfer, an injected claim-UID label and TTL deletion ([releases](https://github.com/kubernetes-sigs/agent-sandbox/releases); [sandboxwarmpool_types.go](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/extensions/api/v1beta1/sandboxwarmpool_types.go)), but nobody has published a measurement of it on k3s, and its managed default NetworkPolicy blocks RFC1918 egress, which would cut off foldrun's in-cluster egress proxy unless set to `Unmanaged` ([sandboxtemplate_types.go](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/extensions/api/v1beta1/sandboxtemplate_types.go)). At foldrun's scale, a hand-rolled pool inside the worker, using the same pattern, is a fair alternative; either way, a one-box cluster is nowhere near the project's ~30 claims/s sharding threshold, so refill speed (gVisor boot plus mounts) is the binding constraint.

> **Question for the owner (1).** The 24 Sep HA review skipped "warm runner pool / pre-pulled AMI" for AWS, while FOL-29's own example recommendation includes "warm pod pool per image". Is a *platform-level* pool of pre-started, tenant-neutral pods, each used for exactly one step and then destroyed, acceptable on the box under "sandbox destroyed after" and "nothing account-level is always on" (`account-pod.ts:6-9`)? The pool is not account-level, but it is always on. This report recommends deciding after the first six actions below have landed and been measured, not before.

AWS changes the picture, because there the image and the node are not already present. The planned layout scales runner nodes from zero with Karpenter; the design itself estimates "~90 seconds" for a pod to land on a new node (`foldrun-infra/prod/karpenter/runners-nodepool.yaml`, design claim, not measured), vendor blogs cite 45–60 s for Karpenter node-ready ([ScaleOps](https://scaleops.com/blog/karpenter-vs-cluster-autoscaler/); [CAST AI](https://cast.ai/blog/karpenter-vs-cluster-autoscaler/)), and a fresh node then pulls the 305 MB slim or 1.7 GB full image from the ECR pull-through cache, since prod-deploy warms only the registry cache, not the nodes (`foldrun-infra/prod/README.md:28-34`). For scale, an AWS test of a 4.9 GB image measured ~49 s from scheduling to container start when pulled and ~3 s when pre-cached ([AWS Containers blog, Oct 2023](https://aws.amazon.com/blogs/containers/reduce-container-startup-time-on-amazon-eks-with-bottlerocket-data-volume/)). Pre-pulling both images onto every node with a DaemonSet when a release lands is not an AMI and fits the rules; a Bottlerocket data-volume snapshot is AMI-adjacent and closer to what the owner skipped. Low-priority placeholder pods, or pool pods at a negative PriorityClass, give node headroom so the next node arrives before a real step needs it ([AWS overprovisioning](https://aws.amazon.com/blogs/containers/eliminate-kubernetes-node-scaling-lag-with-pod-priority-and-over-provisioning/)). One gVisor note for the node choice: the same burst test measured 29.1 s on ARM64 against 17.0 s on x86 at 100 pods, and a maintainer said ARM is "not as mature" ([google/gvisor#13395](https://github.com/google/gvisor/issues/13395)), so x86 runner nodes are the safer default until our own test says otherwise.

> **Question for the owner (2).** Does the 24 Sep skip stand for AWS, given that scale-from-zero means the first step after an idle period waits for a node (45–90 s claimed, unmeasured) plus a cold image pull? The options are to accept that, to keep a minimum of one runner node, or to let a small pool of low-priority pods act as headroom. None of this is needed while production is the single box.

## Ordered plan: instrument, overlap, collapse, then decide on the pool

The actions below are ordered by impact against effort. Items 1–8 need no owner decision and stay inside every constraint (no VMs, no per-customer images, install at runtime, destroy after each step, exactly two runner images). Effort is S (days), M (about a week), L (several weeks). Each item ships in the house order: API → dashboard → CLI → docs → commit and push. New record fields are additions, so they need no API version change.

## What to drop, and what not to build

Several techniques from the comparison should be dropped explicitly, so they stop coming back. **MicroVMs and their snapshots** (Firecracker, Kata, SnapStart, E2B templates, Fly suspend) are ruled out by the owner, and the evidence does not argue for them anyway: Google's gVisor runtime starts faster than its microVM one. **Reusing an environment across steps**, which is where Lambda and Cloud Run get most of their speed, breaks the isolation rule; Lambda's reset after a failed invoke does not even clear `/tmp` ([AWS docs](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)). Knative min-scale and KEDA keep replicas warm *for reuse*, so they are the wrong pool mechanism. **Per-customer images**, GitHub's custom-image direction, are ruled out; the right analogue is what foldrun already has, two shared images plus caches keyed by the declared package set.

Two items from FOL-29's own example should be dropped for the box. **Lazy image pulling** solves a cost the box does not pay: images are local, full is no slower to Ready than slim, k3s's eStargz support is labelled experimental ([k3s blog, 11 Nov 2025](https://docs.k3s.io/blog/2025/11/11/strategies-for-large-images)), stargz-snapshotter restarts can leave running pods with permanent ESTALE ([stargz-snapshotter #2387](https://github.com/containerd/stargz-snapshotter/issues/2387)), and no source has tested runsc on any lazy snapshotter. Pre-pull does the job; revisit SOCI only if AWS nodes join often and the full image still pulls on the step path. **gVisor checkpoint/restore** should wait: on stock k3s and containerd there is no Kubernetes path to `runsc restore` (the gVisor docs offer raw runsc and Docker only, [checkpoint/restore guide](https://gvisor.dev/docs/user_guide/checkpoint_restore/)); containerd is reportedly removing restore-via-CreateContainer in favour of a future RestorePod API, per a single SIG Node post ([sig-node list](https://groups.google.com/a/kubernetes.io/g/sig-node/c/tsdff1ptP-0)); an independent restore took 3.5–4 s, which is slower than our 0.86 s Ready ([agent-substrate #1530](https://github.com/agent-substrate/substrate/issues/1530)); and Google itself says fast-starting workloads generally will not benefit ([GKE Pod snapshots](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/pod-snapshots?authuser=0)). It becomes worth a look only if item 1 shows the driver and SDK spending several seconds in tenant-neutral init that a pool cannot hide.

A few things to avoid while doing the work. Do not delete the 2 s wait without the gate that replaces it. Do not tune runsc boot itself; ~300 ms is not where our seconds are. Do not keep account pods always on to hide their start, which the owner has ruled out; start them earlier instead. Do not report p50 alone: the bursts and cold account pods that hurt users live at p95, which is 2–4× the median in every phase above. Do not judge progress against vendor millisecond claims. And do not keep calling apply → Ready "the cold start": it is the smallest part of what a step waits for, and the name has pointed the work at the wrong phase.

## Conclusion

FOL-29 was framed as a cold-start problem, and by the industry's definition foldrun does not have one: a fresh gVisor pod is Ready in under a second, on par with the best independently measured sandboxes. What foldrun has is a slow, serial and unmeasured hand-off after Ready, made of `kubectl` round trips, a fixed security wait, tree-walking ownership changes and an SDK start-up that has never been timed, plus two design choices that stack waits instead of overlapping them: account pods ensured before the run pod, and an apt cache keyed to a tag that changes with every core release. Those are cheap to fix and need nobody's permission, and fixing them first also makes the warm-pool question answerable with data rather than with other platforms' numbers.

The deeper lesson from Lambda, ARC, AgentCore and agent-sandbox is that "fresh per step" and "warm" are compatible as long as the warm thing is generic and the tenant arrives late, which foldrun's egress-proxy secrets already make easy. A pool is therefore not a question of isolation but of whether the owner wants to pay for always-on platform capacity, on the box and especially on AWS, where scale-from-zero turns today's sub-second Ready into a minute-plus wait for the first step after idle. That is a business decision, and once the per-phase numbers exist it can be made on what the pool would actually save.
